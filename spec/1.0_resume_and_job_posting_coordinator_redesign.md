# Technical Specification (SDD): Asynchronous Batch Coordinator Redesign, Granular State per Tool, and Error History per Revision

## 1. Context and Diagnosis of Current Source Code

The `talent-distiller-agent` system (Python >=3.14) processes `resume` and `job_posting` document types using `anyio`, `claude-agent-sdk`, `labs-agent-lib`, `redis.asyncio` and `starlette`. Based on the inspection of the base source code, the current architecture operates with the following components:

- **Directory Poller (`src/talent_distiller_agent/main.py`)**: Executes two infinite loops in parallel (`process_only_resumes` and `process_job_postings`) via `start_process()`. In each cycle, `_process_directory_batch` sorts eligible files (`SUPPORTED_EXTENSIONS`) by creation date (`get_creation_time`), takes a configurable batch of up to `max_files_per_batch` (`resume_max_files_per_batch` or `job_posting_max_files_per_batch`, default `3` in `Settings`), and invokes `asyncio.gather(*(run_coordinator(str(file_path), doc_type=doc_type) ...), return_exceptions=True)`.
- **State Storage in Redis (`src/talent_distiller_agent/storage/redis_job_store.py`)**: `RedisJobStore` manages hashes prefixed with `resume_job:` and `job_posting:`. It defines base domains in `ExtractionField` (`technical_skills`, `soft_skills`, `certifications`, `languages`) and desirable ones in `DesirableExtractionField` (`desirable_technical_skills`, `desirable_soft_skills`, `desirable_certifications`, `desirable_languages`). Currently, it only stores general metadata in `JobRedisField` (`file_name`, `file_path`, `content`, `session_id`, `completed`, `revision_number`, `correlation_id`), the extracted JSONs per field, and flat, overwritable errors under the prefix `error:<field>`.
- **Guardrails and Lifecycle (`src/talent_distiller_agent/guardrails/coordinator_guardrails.py`)**: `CoordinatorGuardrail` implements `pre_execution_hook`, `post_execution_hook` and `build_sdk_hooks` (`PreToolUse` hook from SDK).
- **Coordinator and Stream Handler (`src/talent_distiller_agent/coordinators/coordinator.py` and `message_stream_handler.py`)**: `run_coordinator` executes `pre_execution_hook`, extracts plain text with `extract_text(file_path)` when `not status.has_content`, builds the prompt with `<pending_tools>` and `<missing_fields>`, invokes `ClaudeSDKClient` and drains the response with `process_coordinator_stream` before calling `post_execution_hook`.
- **Quality and Coverage (`pyproject.toml`)**: The test suite requires `branch = true` and `fail_under = 100` in `pytest-cov`, omitting only `src/talent_distiller_agent/coordinators/main.py`.

## 2. Inconsistencies Detected in the Base Code and Architectural Redesign

The implementing agent MUST correct the following inconsistencies present in the current source code to ensure functional consistency, token economy, and non-blocking processing:

### 2.1. Inconsistency in Retry Limit (`pre_execution_hook` vs. `post_execution_hook`)
- **Current problem**: In `coordinator_guardrails.py`, `post_execution_hook` evaluates `is_max_revision = status.revision_number >= self.settings.coordinator_max_revision_number` and moves the file immediately to `failed_folder` upon finishing attempt N (e.g., attempt 3). However, if an exception occurs during `run_coordinator` (such as a `ValueError` in `extract_text` or a connection failure in `ClaudeSDKClient`), the `try` block jumps to `except Exception` and **never executes `post_execution_hook`**. Then, in the next iteration of the pool, `pre_execution_hook` increments first (`revision_number = await self.tracker.increment_attempts(file_path)`) and compares `if revision_number > max_revisions:` without updating the tools' status to `Failed` nor logging the exceeded attempt limit error in the history.
- **Redesign solution**:
  1. In `pre_execution_hook(file_path)`, **before** incrementing `revision_number`, the current state must be read from Redis (`status = await self.tracker.get_status(file_path)`).
  2. If `status.revision_number >= self.settings.coordinator_max_revision_number`, the coordinator detects that the document reached the maximum allowed revisions when iterating the pool. At that moment, it must:
     * Mark all tool status fields that have not yet been completed (`technical_skills_status`, `soft_skills_status`, `certifications_status`, `languages_status`) as `Failed`.
     * Record in each error history (`technical_skills_error`, `soft_skills_error`, `certifications_error`, `languages_error`) under the current revision key the descriptive message indicating that the maximum attempts (`coordinator_max_revision_number`) were exceeded.
     * Move the file to `self.failed_folder` in a non-blocking manner and return `[]` without invoking the LLM.
  3. In `post_execution_hook(file_path, session_id, stop_reason)`, the file should only be moved to `self.processed_folder` if `status.is_completed` is `True` (which depends on the state of all tools being completed (`technical_skills_status`, `soft_skills_status`, `certifications_status`, `languages_status`)). If it is not yet complete, the file remains in the input folder so that in the next pool iteration `pre_execution_hook` retrieves the state and evaluates whether to retry the pending tools or if it has already reached `coordinator_max_revision_number` and must be moved to `failed_folder` and record the errors as a cumulative history by revision number (`technical_skills_error`, `soft_skills_error`, `certifications_error`, `languages_error`).

### 2.2. Lack of Per-Tool States and Overwritten History in Redis
- **Current problem**: `RedisJobStore.save_agent_error` executes `await self.redis.hset(key, f"{self.ERROR_FIELD_PREFIX}{field}", error_msg)` and `save_agent_result` executes `pipe.hdel(key, f"{self.ERROR_FIELD_PREFIX}{field}")`. This destroys the error history between retries and does not expose the individual state (`Called`, `Completed`, `Failed`) of each tool.
- **Redesign solution**:
  * Incorporate the 4 status fields in the Redis hash and in `UnifiedResumeJob` / `UnifiedJobPostingJob`: `technical_skills_status`, `soft_skills_status`, `certifications_status`, `languages_status`.
  * Incorporate the 4 error history fields as JSON maps (`dict[str, str]` indexed by `str(revision_number)`): `technical_skills_error`, `soft_skills_error`, `certifications_error`, `languages_error`.
  * Never delete previous `<tool>_error` entries when a tool succeeds in a subsequent revision; the map preserves the historical traceability of what failed in each revision (`"1"`, `"2"`, etc.).

### 2.3. Race Condition between Phase 1 (`<formatted_...>`) and the `PreToolUse` Hook (Token Economy and Latency)
- **Current problem**: In `coordinator.py`, when `not status.has_content`, the raw text is sent to the LLM so that in Phase 1 it emits `<formatted_resume>` or `<formatted_job_posting>` and in the same turn invokes the MCP tools. However, in `ClaudeSDKClient`, the `PreToolUse` hook (`_validate_tool_use` in `coordinator_guardrails.py`) is triggered before `process_coordinator_stream` processes the text block or when the model emits text and tool calls simultaneously. If after 0.5 seconds (`5 * 0.1s`) `status.has_content` remains `False`, the guardrail denies all tools (`permissionDecision: "deny"`), wasting turn 1 tokens without executing any extraction.
- **Redesign solution**:
  * When `not status.has_content` in `run_coordinator`, after extracting `raw_text` with `extract_text(file_path)`, an initial content checkpoint must be persisted immediately in Redis (`await tracker.save_content(file_path, raw_text)`) **before** starting `ClaudeSDKClient`, keeping the `<resume_content>` or `<job_posting_content>` block in the prompt so that when the LLM emits `<formatted_resume>` / `<formatted_job_posting>` in `process_coordinator_stream`, it updates and overwrites said content with `await tracker.save_content(resume_path, formatted_content)`.
  * This way, `status.has_content` is already `True` when the `PreToolUse` hooks are triggered in the first turn, eliminating false blocks and unnecessary waits. If `raw_text` is empty, the exception is logged in all `<tool>_error` of the current revision and the `<tool>_status` are marked as `Failed`.

### 2.4. Prevention of I/O Blocking and Overlap in the Batch Pool
- **Current problem**:
  1. In `coordinator.py`, `extract_text(file_path)` is invoked synchronously on the main event loop.
  2. In `coordinator_guardrails.py`, `file_writer(file_path, ...)` is invoked synchronously on the main event loop.
  3. In `main.py`, if a polling cycle overlaps or is invoked concurrently, there is no filter for in-flight files.
- **Redesign solution**:
  1. Execute `extract_text` and `file_writer` using `await anyio.to_thread.run_sync(...)` (consistent with `talent_distiller_agent/api/_uploads.py`).
  2. In `main.py`, maintain a set of active in-flight files (`_in_flight_files: set[Path]`) to ensure that no file currently being processed is mistakenly selected in another concurrent batch, releasing it in a `finally` block.

## 3. Detailed Specification of the Redis State Model

### 3.1. New Enumerations in `src/talent_distiller_agent/storage/redis_job_store.py`

1. **`ToolStatus(StrEnum)`**:
   Defines the three valid states for each extraction tool:
   ```python
   class ToolStatus(StrEnum):
       """Execution lifecycle state for each extraction tool."""
       CALLED = "Called"
       Completed = "Completed"
       FAILED = "Failed"
   ```
2. **`ToolStatusField(StrEnum)`**:
   ```python
   class ToolStatusField(StrEnum):
       """Redis hash fields tracking per-tool status."""
       TECHNICAL_SKILLS = "technical_skills_status"
       SOFT_SKILLS = "soft_skills_status"
       CERTIFICATIONS = "certifications_status"
       LANGUAGES = "languages_status"
   ```
3. **`ToolErrorField(StrEnum)`**:
   ```python
   class ToolErrorField(StrEnum):
       """Redis hash fields tracking per-tool error history across revisions."""
       TECHNICAL_SKILLS = "technical_skills_error"
       SOFT_SKILLS = "soft_skills_error"
       CERTIFICATIONS = "certifications_error"
       LANGUAGES = "languages_error"
   ```

### 3.2. Mapping Rules between Base Tools and Document Fields (`RESUME` vs. `JOB_POSTING`)
- There are 4 base tools defined in `ExtractionField`: `technical_skills`, `soft_skills`, `certifications`, `languages`.
- For `DocumentType.RESUME`, a base tool `<tool>` reaches `ToolStatus.Completed` when the `<tool>` field has been successfully validated and saved in Redis.
- For `DocumentType.JOB_POSTING`, each base tool produces both mandatory requirements (`<tool>`) and desirable ones (`desirable_<tool>`) according to `STORAGE_SPECS[DocumentType.JOB_POSTING]` and `_save_tool_output`. Therefore:
  * `<tool>_status` changes to `ToolStatus.Completed` only when **all** target fields associated with that tool (`self.get_target_fields_for_base_field(base_field)`) exist and are valid in Redis.
  * If any of the fields associated with `<tool>` fails or remains pending at the end of the turn, `<tool>_status` changes to `ToolStatus.FAILED` and the error is recorded in `<tool>_error[str(revision_number)]`.

### 3.3. Initialization Structure in `RedisJobStore.init_or_get_state(file_path)`
When `await self.redis.hgetall(key)` returns empty (the document does not yet have an initial state in Redis), `init_or_get_state` MUST create the initial hash with the following fields:
```python
initial_data: dict[str, str] = {
    JobRedisField.FILE_NAME: Path(file_path).name,
    JobRedisField.FILE_PATH: file_path,
    JobRedisField.COMPLETED: self._encode_bool(False),
    JobRedisField.REVISION_NUMBER: "0",
    JobRedisField.CORRELATION_ID: uuid.uuid4().hex,
    ToolStatusField.TECHNICAL_SKILLS: ToolStatus.CALLED,
    ToolStatusField.SOFT_SKILLS: ToolStatus.CALLED,
    ToolStatusField.CERTIFICATIONS: ToolStatus.CALLED,
    ToolStatusField.LANGUAGES: ToolStatus.CALLED,
    ToolErrorField.TECHNICAL_SKILLS: "{}",
    ToolErrorField.SOFT_SKILLS: "{}",
    ToolErrorField.CERTIFICATIONS: "{}",
    ToolErrorField.LANGUAGES: "{}",
}
```
- If the state already existed in Redis, `init_or_get_state` must ensure that if any of the `*_status` or `*_error` fields are not present in the retrieved hash, they are filled by default with `ToolStatus.CALLED` (or `ToolStatus.Completed` if their data fields are already extracted) and `"{}"` respectively.

### 3.4. Structure of the Error Maps (`<tool>_error`)
- Each `<tool>_error` field (`technical_skills_error`, `soft_skills_error`, `certifications_error`, `languages_error`) is stored in Redis as a JSON string representing a dictionary `dict[str, str]` where:
  * **Key**: Revision number in string format (`str(revision_number)`, e.g., `"1"`, `"2"`, `"3"`).
  * **Value**: Description of the error or exception that occurred in that revision.
- If multiple errors occur for the same tool in the same revision (for example, in `JOB_POSTING`), they are concatenated with `"; "` under the same `str(revision_number)` key without overwriting or losing previous details.
- Example of state in Redis after failing in revisions 1 and 2 and reaching `coordinator_max_revision_number = 2`:
  ```json
  {
    "technical_skills_status": "Failed",
    "technical_skills_error": "{\"1\": \"Invalid JSON output: bad_json\", \"2\": \"Maximum revision attempts (2) reached without completing extraction.\"}"
  }
  ```

### 3.5. Update of `JobStatus` and Pydantic Models (`UnifiedResumeJob` and `UnifiedJobPostingJob`)
1. In `JobStatus` (`redis_job_store.py`):
   * Add:
     * `tool_statuses: dict[str, ToolStatus]` (mapping each `ExtractionField` to its `ToolStatus`).
     * `tool_errors: dict[str, dict[str, str]]` (mapping each `ExtractionField` to its error history per revision).
   * The `is_completed` property must return `True` when `self.has_content`, `not self.missing_fields` and all values in `self.tool_statuses.values()` are `ToolStatus.Completed`.
2. In `UnifiedResumeJob` (`redis_job_store.py`):
   * Add the typed fields with default values and JSON validator from Redis:
```python
technical_skills_status: ToolStatus = ToolStatus.CALLED
soft_skills_status: ToolStatus = ToolStatus.CALLED
certifications_status: ToolStatus = ToolStatus.CALLED
languages_status: ToolStatus = ToolStatus.CALLED

technical_skills_error: dict[str, str] = Field(default_factory=dict)
soft_skills_error: dict[str, str] = Field(default_factory=dict)

```
   * Add a `@field_validator` (`mode="before"`) for `technical_skills_error`, `soft_skills_error`, `certifications_error`, `languages_error` that parses JSON strings coming from Redis into `dict[str, str]` (returning `{}` if it is empty or `None`).
   * Keep the field `errors: dict[str, str] = Field(default_factory=dict)` for backward compatibility.

## 4. Coordinator Flow and Guardrails Specification

### 4.1. New Methods in `RedisJobStore` (`src/talent_distiller_agent/storage/redis_job_store.py`)
Implement or update the following methods in `RedisJobStore`:

1. **`mark_tools_called(self, file_path: str, base_fields: list[str] | tuple[str, ...]) -> None`**:
   * For each `base_field` in `base_fields` (e.g., `"technical_skills"`), updates its `<base_field>_status` field in Redis to `ToolStatus.CALLED`.
2. **`save_agent_result(self, file_path: str, field: str, raw_json: str) -> None`**:
   * Validates `raw_json` with `AGENT_JSON_ADAPTER`.
   * If it raises `ValidationError`, invokes `await self.save_agent_error(file_path, field, f"Invalid JSON output: {raw_json}")` and returns.
   * If it is valid, saves `field` in the Redis hash and verifies if all target fields (`get_target_fields_for_base_field(base_field)`) are already present in Redis.
   * If all target fields of that base tool are present, updates `<base_field>_status = ToolStatus.Completed` within the same Redis transaction/pipeline.
3. **`save_agent_error(self, file_path: str, field: str, error_msg: str, revision_number: int | None = None) -> None`**:
   * Determines the base tool (`base_field = field.removeprefix(DESIRABLE_PREFIX)`).
   * If `base_field` belongs to `ExtractionField`:
     * Obtains the current `revision_number` from the state in Redis if not provided by parameter (using `"1"` as a minimum if it is still `"0"`).
     * Reads the current JSON map for `<base_field>_error` in Redis, adds or concatenates `error_msg` in the `str(revision_number)` key, writes the updated JSON to `<base_field>_error` and updates `<base_field>_status = ToolStatus.FAILED`.
   * It also keeps writing to `f"{self.ERROR_FIELD_PREFIX}{field}"` for backward compatibility with `errors`.
4. **`mark_max_revisions_exceeded(self, file_path: str, max_revisions: int) -> None`**:
   * Retrieves the current state with `init_or_get_state(file_path)`.
   * Obtains the revision key `rev_key = str(state.get(JobRedisField.REVISION_NUMBER, max_revisions))`.
   * For each of the 4 tools (`technical_skills`, `soft_skills`, `certifications`, `languages`):
     * Sets `<tool>_status = ToolStatus.FAILED`.
     * Loads the `<tool>_error` map, and adds or concatenates in `error_map[rev_key]` the descriptive message: `f"Maximum revision attempts ({max_revisions}) reached without completing extraction."`.
   * Sets `JobRedisField.COMPLETED = "0"` and atomically persists all changes to Redis with `pipeline(transaction=True)`.
5. **`fail_unprocessed_tools(self, file_path: str, error_msg: str) -> None`**:
   * Method invoked when a global exception occurs in `run_coordinator` or when the agent's stream ends and a tool that was dispatched (`ToolStatus.CALLED`) did not produce a result.
   * For every tool whose `<tool>_status != ToolStatus.Completed`:
     * Changes `<tool>_status` to `ToolStatus.FAILED`.
     * If in the current revision (`str(revision_number)`) it did not yet have a registered error in `<tool>_error`, it registers `error_msg` under the `str(revision_number)` key.

### 4.2. Flow in `CoordinatorGuardrail` (`src/talent_distiller_agent/guardrails/coordinator_guardrails.py`)

1. **`pre_execution_hook(self, file_path: str) -> list[str]`**:
   * Calls `status = await self.tracker.get_status(file_path)` (which ensures that `init_or_get_state` creates the initial state with the `*_status = "Called"` and `*_error = "{}"` if the document is new).
   * **Step A (Already completed)**: If `status.is_completed`:
     * Calls `await self.tracker.save_session_and_completion(file_path, is_completed=True)`.
     * Moves the file in a non-blocking manner to `self.processed_folder` (`await anyio.to_thread.run_sync(file_writer, file_path, self.processed_folder)`).
     * Returns `[]`.
   * **Step B (Verification of `coordinator_max_revision_number`)**:
     * Evaluates `if status.revision_number >= self.settings.coordinator_max_revision_number:`.
     * If met:
       * Calls `await self.tracker.mark_max_revisions_exceeded(file_path, self.settings.coordinator_max_revision_number)`.
       * Moves the file to `self.failed_folder` (`await anyio.to_thread.run_sync(file_writer, file_path, self.failed_folder)`).
       * Logs the error and returns `[]`.
   * **Step C (Preparation for New Attempt / Revision)**:
     * Increments the attempt in Redis: `revision_number = await self.tracker.increment_attempts(file_path)`.
     * Identifies pending base tools: those whose associated fields are in `status.missing_fields` (or whose `status.tool_statuses[base_field] != ToolStatus.Completed`).
     * Marks these pending tools as `ToolStatus.CALLED` in Redis via `await self.tracker.mark_tools_called(file_path, pending_base_fields)`.
     * Returns the deduplicated list of MCP tool names (`FIELD_TO_MCP_TOOL[field]`) only for the missing fields (token economy: never re-executes tools already in `Processed` state).

2. **`post_execution_hook(self, file_path: str, session_id: str | None, stop_reason: str | None = None) -> None`**:
   * If any tool remained in `ToolStatus.CALLED` without having completed all its fields at the end of the stream, invokes `await self.tracker.fail_unprocessed_tools(file_path, f"Tool did not complete in revision (stop_reason={stop_reason})")`.
   * Gets the updated `status = await self.tracker.get_status(file_path)`.
   * Saves the session and completeness flag with `await self.tracker.save_session_and_completion(file_path=file_path, is_completed=status.is_completed, session_id=session_id)`.
   * **If `status.is_completed` is `True`**:
     * Moves the file to `self.processed_folder` (`await anyio.to_thread.run_sync(file_writer, file_path, self.processed_folder)`).
   * **If `status.is_completed` is `False`**:
     * Does **not** move the file to `failed_folder` at this point; leaves the file in the directory so that in the next iteration of the document pool `pre_execution_hook` verifies `status.revision_number >= self.settings.coordinator_max_revision_number`, records the failure due to maximum attempts in each `<tool>_error`, updates all `<tool>_status` to `Failed` and moves the file to `failed_folder`.

### 4.3. Exception Handling in `run_coordinator` (`src/talent_distiller_agent/coordinators/coordinator.py`)
- In `run_coordinator(file_path, doc_type)`:
  * Execute `raw_text = await anyio.to_thread.run_sync(extract_text, file_path)` when `not status.has_content`.
  * If `not raw_text or not raw_text.strip()`:
    * Invoke `await tracker.save_agent_error(file_path, JobRedisField.CONTENT, "extract_text returned empty content.")`.
    * Invoke `await tracker.fail_unprocessed_tools(file_path, "ValueError: Empty text extracted from document")`.
    * Raise `ValueError(f"Empty text extracted from {file_path}")`.
  * If `raw_text` is valid, immediately save the initial text in Redis (`await tracker.save_content(file_path, raw_text)`) to prevent the `PreToolUse` hook from blocking parallel calls in the first turn, keeping the sending of `<resume_content>` / `<job_posting_content>` in the prompt so that the coordinator emits the `<formatted_...>` block and updates the structured content in `process_coordinator_stream`.
  * In the `except Exception as exc:` block of `run_coordinator`:
    * Record the exception in the `<tool>_error` fields of the current revision for all tools that are not in `Processed` by calling:
      `await tracker.fail_unprocessed_tools(file_path, f"{type(exc).__name__}: {exc}")`.

### 4.4. Asynchronous Batch Processing in `src/talent_distiller_agent/main.py`
- In `_process_directory_batch(directory, doc_type, max_files_per_batch)`:
  * Maintain an in-memory set `_in_flight_files: set[Path] = set()` at the module level.
  * Filter the files in the directory (`path.is_file() and path.suffix.lower() in SUPPORTED_EXTENSIONS and path not in _in_flight_files`), sort them by `get_creation_time` and take up to `max_files_per_batch`.
  * Register the selected files in `_in_flight_files` before launching `asyncio.gather` and ensure their removal in a `finally` block upon concluding the batch.
