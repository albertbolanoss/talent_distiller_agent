REQUERIMIENTO REFINADO: estado y error por skill durante la extraccion
================================================================================

OBJETIVO ORIGINAL (resumen de lo pedido)
-------------------------------------------
Mientras el coordinador reintenta (revision_number) la extraccion de
technical_skills/soft_skills/certifications/languages, poder saber por cada una:
  - si ya se obtuvo (pending/failed)
  - el error puntual del MCP server si fallo
Y decidir donde vive ese estado (coordinador vs mcp-skills-extractor-agents), y si
un job ya fallido (reviso_number agotado) deberia poder reiniciarse.

Este documento es la version refinada de ese requerimiento: mismo objetivo, pero
ajustada para ser simple, escalable, tolerante a fallos y barata en tokens,
reutilizando lo que el proyecto YA tiene en vez de duplicar estado.

--------------------------------------------------------------------------------
1. DONDE DEBE VIVIR ESTE ESTADO: coordinador (RedisJobStore), NO
   mcp-skills-extractor-agents
--------------------------------------------------------------------------------
mcp-skills-extractor-agents debe seguir siendo un servicio SIN estado: recibe
texto + doc_type en una llamada MCP, y devuelve una lista JSON o lanza un error.
No conoce "archivo", "revision_number" ni "job" - ese es su contrato actual
(ver extract_technical_skills en el repo candidate-skill-agent) y es lo correcto:

  - Un tool-server con estado no se puede escalar/reiniciar libremente (cada pod
    tendria que compartir ese estado igual que hoy se comparte Redis - no gana
    nada duplicandolo ahi).
  - Acopla ambos proyectos: cualquier coordinador futuro que use estas tools
    (no solo talent-distiller-agent) heredaria ese estado sin pedirlo.
  - El coordinador YA es el dueno de todo el ciclo de vida del job (revision_number,
    completed, content, errores por campo) en
    src/talent_distiller_agent/storage/redis_job_store.py. Agregar el estado ahi
    es simplemente extender un patron que ya existe, no crear uno nuevo.

Conclusion: todo lo de este documento se implementa en talent-distiller-agent
(RedisJobStore + el modelo unificado), cero cambios en mcp-skills-extractor-agents.

--------------------------------------------------------------------------------
2. EL ERROR POR CAMPO YA EXISTE - NO DUPLICARLO
--------------------------------------------------------------------------------
`RedisJobStore.save_agent_error(file_path, field, error_msg)` ya escribe
`error:<field>` en el hash de Redis, y ya se limpia solo (`hdel`) cuando el campo
se guarda con exito (`save_agent_result`). `unify_by_filename` ya expone esto como
`errors: dict[str, str]` en el resultado final. Es decir, "tecnical_skill_error"
que pediste YA esta resuelto hoy como `errors["technical_skills"]` (vacio/ausente
si no hubo error). No se necesita ningun campo nuevo para esto.

--------------------------------------------------------------------------------
3. LO QUE SI FALTA: el STATUS (pending/success/failed) por campo
--------------------------------------------------------------------------------
Propuesta: NO agregar un campo nuevo que haya que escribir y mantener
sincronizado (mas estado = mas superficie de bugs). En vez de eso, CALCULARLO a
partir de datos que ya existen, igual que ya se calcula `JobStatus.is_completed`
y `missing_fields`:

    status(field) =
      "success"  si el campo ya tiene un valor guardado (igual que hoy define
                  `missing_fields`)
      "failed"   si el campo sigue vacio Y `revision_number >= max_revisions`
                  (el job ya agoto sus intentos)
      "pending"  en cualquier otro caso (todavia dentro del presupuesto de
                  revisiones, sin valor aun)

Esto da exactamente el `technical_skill_status: pending|failed` que pediste, sin
que nadie tenga que escribirlo explicitamente ni pueda quedar desincronizado del
`revision_number` real.

Forma de exponerlo (consistente con como ya se expone `errors`): un diccionario,
no 4-8 campos sueltos (technical_skill_status, soft_skill_status, ...). Un dict
escala solo si mas adelante se agregan mas extraction fields (ya hay 4 + 4
"desirable_*" para job postings = 8 campos hoy):

    {
      "technical_skills": "success",
      "soft_skills": "pending",
      "certifications": "failed",
      "languages": "success"
    }

Cambios concretos (pequenos, todos en talent-distiller-agent):
  - storage/redis_job_store.py:
    - Agregar un StrEnum `FieldStatus` (PENDING/SUCCESS/FAILED) junto a
      `ExtractionField`.
    - Agregar un metodo en `RedisJobStore` (o en `JobStatus`) que, dado el
      estado crudo de Redis + `self.settings.coordinator_max_revision_number`,
      devuelva `dict[str, FieldStatus]` para `self.extraction_fields`.
    - En `unify_by_filename`, incluir ese dict como `statuses` en el payload.
  - En `UnifiedResumeJob` (y por herencia `UnifiedJobPostingJob`): agregar
    `statuses: dict[str, str] = Field(default_factory=dict)`.

No se requiere ninguna escritura nueva a Redis para esto - es derivado en el
momento de leer, igual que `missing_fields` hoy.

--------------------------------------------------------------------------------
4. REINICIAR UN JOB FALLIDO (tu idea de resetear si se re-encola)
--------------------------------------------------------------------------------
Hoy, si un archivo ya fallido (`revision_number > max_revisions`, movido a
`failed/`) se vuelve a mover a la carpeta vigilada (`resume_dir`/`job_posting_dir`)
para reintentar, el guardrail lo vuelve a marcar failed en el primer intento
(sigue viendo `revision_number` por encima del limite) - nunca llega a reintentar
nada. Hace falta un reset explicito, pero ACOTADO: si el root cause es permanente
(ej. el MCP server sigue caido), reiniciar sin limite quemaria tokens en un loop
infinito cada vez que alguien reencole el archivo.

Propuesta (minima, reutiliza el mismo mecanismo de carpetas que ya existe):

  - Nuevo campo en Redis: `retry_cycles` (entero, arranca en 0).
  - Nuevo setting: `coordinator_max_retry_cycles` (default bajo, ej. 1 o 2 -
    "le damos como maximo N reintentos completos antes de requerir intervencion
    humana real, no solo volver a soltar el archivo en la carpeta").
  - En `CoordinatorGuardrail.pre_execution_hook`, ANTES del chequeo actual de
    `revision_number > max_revisions`:

        if status.revision_number > max_revisions and not status.is_completed:
            if retry_cycles < max_retry_cycles:
                # reencolado: dar otra vuelta completa
                await tracker.reset_for_retry(file_path)  # revision_number=0,
                                                            # retry_cycles += 1,
                                                            # NO borra campos ya
                                                            # exitosos (no se
                                                            # re-extraen - barato
                                                            # en tokens)
                # continua el flujo normal con missing_fields actualizado
            else:
                # ya se le dieron sus reintentos - failed otra vez, requiere
                # revision humana real
                ...

  - Importante: `reset_for_retry` NO borra `technical_skills`/`soft_skills`/etc.
    que ya tengan valor - solo resetea `revision_number` y limpia `error:<field>`
    de los campos que sigan vacios. Asi el reintento solo gasta LLM/tool-calls en
    lo que realmente falta, no repite trabajo ya hecho (clave para "uso de tokens
    adecuado").

--------------------------------------------------------------------------------
5. MODO DESARROLLADOR
--------------------------------------------------------------------------------
Nada de esto es especifico de Kubernetes: todo vive en Redis + `Settings` (ya
env-driven via `.env` en dev, via ConfigMap en el cluster). Corriendo local con un
Redis local, el mismo codigo aplica sin cambios - no hace falta ninguna rama
"modo dev" separada. Esa es, de hecho, la razon para preferir "calcular el status"
en vez de agregar un pipeline de escritura nuevo: menos piezas que puedan
comportarse distinto entre entornos.

--------------------------------------------------------------------------------
6. FUERA DE ALCANCE (a proposito, para mantenerlo simple)
--------------------------------------------------------------------------------
NO incluido en esta propuesta (quedan como mejoras futuras opcionales, no
bloquean esto):
  - Distinguir "error de infraestructura" vs "error de contenido" para cortar
    revisiones antes de los 10 intentos (ver coordinator_revision_design_analysis.txt
    - es un problema real, pero es un cambio de comportamiento mas grande que
    merece su propia discusion, no mezclarlo con el tracking de estado).
  - Backoff exponencial entre revisiones.
  - Alertas/automatizacion sobre archivos en `failed/` (lo pediste como "para
    revision humana y posteriores automatizaciones" - esto solo deja el dato
    (`statuses`, `errors`, carpeta `failed/`) disponible para que esa
    automatizacion futura lo consuma; no se esta construyendo esa automatizacion
    aqui).
